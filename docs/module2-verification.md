## 1. How this data was produced

One uninterrupted invocation of `.venv/bin/python verify.py`, all eight scenarios in
`order`, no per-scenario re-runs and no splicing. Every figure below comes from that single
run and from the decision log entries it wrote (`logs/decision_log.jsonl` lines 550–681,
reproduced in the appendix).

One environment note, because it is not incidental. The run was invoked with the inherited
Claude Code session variables cleared:

```bash
env -u ANTHROPIC_BASE_URL -u CLAUDE_CODE_ENTRYPOINT -u CLAUDECODE \
    -u CLAUDE_CODE_OAUTH_SCOPES -u CLAUDE_CODE_SDK_HAS_HOST_AUTH_REFRESH \
    -u CLAUDE_CODE_SESSION_ID -u CLAUDE_CODE_MESSAGING_SOCKET \
    -u CLAUDE_CODE_MESSAGING_TOKEN \
    .venv/bin/python verify.py
```

The SDK subprocess otherwise inherits those variables and prefers subscription auth over the
`ANTHROPIC_API_KEY` that `verify.py` loads from `.env` — see
[§4.1](#41-authentication-failures-were-reported-as-agent-failures-fixed). Run from an
ordinary terminal this is not needed.

Every entry from this run is tagged `run_source: "live"`
([§4.4](#44-no-guardrail-has-ever-fired-in-a-live-run)).

## 3. `contra_indicators` — assessment

Populated in all five assessed scenarios, 4–6 entries each, substantive throughout. The test
applied: does each entry make an argument that would change the code if true, or is it a
restatement of a caveat?

**`cracked_hob` is the strongest case**, because the model wrote out precisely why a weighed
call would have gone the other way, and then did not go that way:

> "Appliance is only 4.2 years old against a 12–15 year expected life for a ceramic hob, so
> on age alone it is early to replace"

> "Repair at GBP 165 of GBP 389 is 42%, comfortably inside the 70% boundary, which on
> economics alone would read as B"

That is the determinative rule being applied deliberately rather than by accident: the model
identified both repair-leaning signals, recorded them as arguments against its own answer,
and still returned A.

**`likely_replacement`** attacked its own key factor and named the condition that would flip
the code:

> "Element and thermostat are classic repair-leaning fault classes and are individually cheap
> parts — if it is only the element, the true repair cost is well under GBP 310 and this is a
> clear B"

**`resident_rejects`** and **`parts_delayed`** each surfaced a data-quality problem in
Iterum's own seed data unprompted — replacement cost recorded inconsistently (£329 vs £259),
and a cost ratio that changes depending on which replacement figure is used.

**Assessment: the field is doing its job.** The skill's stated purpose — showing whether the
model had already seen the reason it was later overruled — is met in every case. Since this
work, an empty `contra_indicators` on a non-determinative call is a hard validation error
rather than an advisory ([§4.2](#42-empty-contra_indicators-parsed-cleanly-fixed)).

**One limit stands:** one generation per scenario. Nothing here speaks to consistency across
repeat runs.

## 4. What did not work

Four entries plus a harness defect. Three are fixed; one is not.

### 4.1 Authentication failures were reported as agent failures (fixed)

An earlier full run reported four scenarios as behavioural failures — "never messaged the
resident", "complete_triage never called". They were not. Those scenarios never reached the
model. The cause was visible only on the event bus:

```json
{"kind": "agent_text", "text": "Your organization has disabled Claude subscription access
          for Claude Code · Use an Anthropic API key instead"}
{"kind": "phase_result", "subtype": "success", "is_error": true, "cost_usd": 0.0}
```

The SDK does not raise on an auth rejection — it returns a successful-looking result whose
*text* happens to be the error — so no exception fired, no `run_error` was logged, and
`decision_log.jsonl` showed only `run_complete` with `tool_calls: 0`. `_drain` in
`agent/runner.py` published `is_error: true` and nothing consumed it.

**Fixed.** `verify.py` now has `environment_failure()`, keyed on `is_error`, on runner `error`
events, and on a run that called nothing and spent nothing. Such scenarios are excluded from
the pass total, announced in a separate block, and the process exits 1. Verified end-to-end
against an invalid key. This run reported no environment failures: all eight scenarios spent
real money and made real tool calls.

The failure was also intermittent — a later run with the inherited environment succeeded — so
it is not a standing organisation policy. CLAUDE.md's gotcha "The Agent SDK does not read
`.env`" is correct but incomplete: loading `.env` is not sufficient when the environment also
offers subscription credentials, because those win.

### 4.2 Empty `contra_indicators` parsed cleanly (fixed)

The requirement that a weighed call must argue against itself lived only in the Pydantic field
description, which makes it advisory. An empty list parsed without complaint and was
indistinguishable from the model having genuinely found nothing to say — a silent loss of
exactly the signal the field exists to collect.

**Fixed.** `RepairVsReplace` now carries a `model_validator` requiring `contra_indicators` to
be non-empty when `determinative is False`. Determinative calls stay exempt by design. A
violation surfaces as a fallback to the heuristic with the reason on the `reasoning_path`
event, rather than as a failed run.

### 4.3 The evidence ladder was overwritten at submission (NOT fixed)

**Severity: high. This is the real defect this run surfaced.**

`cracked_hob` is the scenario where no photograph can be obtained. The skill's ladder is
explicit for that case: *"Photo requested and not supplied, or unclear: assess at 0.6 or below
with the ambiguity named in `evidence_gaps`."* The assessment did exactly that —

```json
{"code": "A", "confidence": 0.6, "determinative": true,
 "meets_threshold": false, "confidence_threshold": 0.75}
```

— and named the gap first in its list:

> "No photograph of the crack on record — this is the cheapest evidence available and would
> move confidence to ~0.95 or reclassify the fault entirely"

The agent then called `submit_recommendation` with **0.78**.

That is not rounding. The skill capped confidence at 0.6 *specifically because the evidence
was missing*, and the submitted value clears the 0.75 threshold that gates downstream
behaviour. The cap was computed correctly, recorded correctly, and discarded one tool call
later. Nothing validates that the two agree, and the decision log stores both — so an analysis
reading `submit_recommendation` and one reading `assess_repair_vs_replace` would report
different confidence, and different threshold compliance, for the same job.

This is the same failure shape as §4.1 and §4.4: a signal produced correctly, then lost
because nothing downstream is obliged to respect it. Note that this suite's checks read the
*assessment* via `_assessment()`, so `cracked_hob` scored 13/13 while this was happening —
**no check covers agreement between the two.**

The fix is for `submit_recommendation` to reject a confidence that differs materially from the
assessed value, or to stop taking confidence as a parameter and read it from the assessment.

### 4.4 No guardrail has ever fired in a live run

`decision_log.jsonl` contains 30 `guardrail_block` entries. **None came from a scenario run.**
All were written by `selftest.py` calling the `PreToolUse` hook directly through the same
`log_decision` path. In this run, live guardrail blocks: **zero**.

**Partly fixed.** `log_decision` now stamps every entry with `run_source`, set to `"selftest"`
by `selftest.py` and `"live"` otherwise, so the two are distinguishable. Every entry from this
run is tagged `"live"`. Entries written before the change carry `null` — honest, since they
predate the distinction and cannot be reclassified retroactively.

What the tag cannot fix is the underlying fact: the agent routed correctly in every scenario
and never attempted a blocked tool, so the guardrails were never reached. In `in_warranty` it
identified the warranty position and escalated to ops without attempting `book_visit`; in
`guardrail_emergency` it halted at first contact. That is a good result, and it means **these
live runs are no evidence that the guardrails work.** That evidence comes only from
`selftest.py`, which exercises them synthetically. Both facts belong together.

### 4.5 A harness defect invalidated the previous sweep (fixed)

Recorded because it changes how earlier results should be read.

`BUS.subscribe()` replays history to every new subscriber, and `run_one` subscribed its
`Recorder` *before* `run_scenario` called `BUS.reset()`. Every scenario therefore began
holding the previous scenario's entire event stream. Only the first scenario in a sweep was
clean.

The previous sweep reported `cracked_hob` 11/13 and `resident_rejects` 5/7. Both sets of
failures were artifacts:

- `cracked_hob` "1 PM gate opened" — `send_email` was never called; that gate was
  `likely_replacement`'s. Its own gate logged `eng=True, pm=False, over=False`.
- `cracked_hob` "engineer confirmed BEFORE booking" — `_approvals_precede_booking` computes
  `booked_at = min(seq)` over replacement allows, which selected `likely_replacement`'s
  booking, making the engineer's confirmation look late.
- `resident_rejects` "4 slots proposed" against a limit of 3 — `parts_delayed`'s one slot plus
  its own three.

**This retracts a claim in the previous version of this document**, which described the
`resident_rejects` slot overflow as a genuine defect and offered a check-then-append race as
the likely mechanism. That was wrong. The scenario had never been run in isolation; both
observations of it followed `parts_delayed`. On this clean run it proposed three slots and
passed 7/7. The slot limit works.

**Fixed** by resetting the bus before the `Recorder` subscribes. Confirmed directly: with a
prior scenario's events in history, a new recorder now inherits `['reset']` alone.

## 6. `determinative` — now has evidence

The previous version of this document recorded `determinative` as untested: the branch fires
only on `hob_surface_damage`, no scenario carried that slug, and `false` is the field default,
so the assessed scenarios showed only that it was not spuriously set.

`scenarios/cracked_hob.json` closes that. It is built so the fixed-outcome rule has to *beat*
the six factors rather than agree with them:

| Signal | Value | Argues for |
|---|---|---|
| Age | 4.16 years, inside the 7-year line | repair |
| Cost ratio | £165 / £389 = 42%, inside the 70% boundary | repair |
| Fault class | `hob_surface_damage` | **A, determinative** |

Result:

```json
{"code": "A", "determinative": true, "confidence": 0.6,
 "inputs": {"age_years": 4.16, "cost_ratio": 0.424, "in_warranty": false}}
```

Both weighed signals argued for repair, the model recorded both in `contra_indicators` (§3),
and the code was still A. Had the code tracked age or ratio here, the determinative list would
not be doing anything.

Routing was correct in both directions and not over-escalated: the replacement went through
engineer confirmation, and at £389 — under the £400 threshold — no PM approval was sought
(`eng=True, pm=False, over=False`). The skill's claim that *"routing is unchanged"* for a
determinative call holds.

**Still untested: the upper rung of the ladder.** The 0.95 "crack confirmed by photo" arm is
**unreachable**, not merely unexercised. `photos` on the issue record appears nowhere in
`agent/`, and there is no `request_photo` or attachment tool — a photograph cannot be supplied
to this system at all. `cracked_hob` therefore tests the lower rung ("requested and not
supplied", capped at 0.6), which is the only rung the architecture can currently reach.
Testing 0.95 requires building photo plumbing first.

The ladder is also what the agent overrode at submission (§4.3) — so the one rung that *is*
reachable is correctly computed and then not respected.
