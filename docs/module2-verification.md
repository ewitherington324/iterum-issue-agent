# Module 2 — skill verification run

Verification of the three Module 2 skill files (`iterum-triage-steps`,
`iterum-repair-vs-replace`, `iterum-escalation`) against all seven scenarios in
`scenarios/`, using `verify.py` — the live path, real model calls, no mocking of the
reasoning steps.

**Date:** 2026-09-18 · **Model:** `claude-opus-5` · **Resident simulator:** `claude-haiku-4-5`
**Result:** 52 / 54 checks passed across seven scenarios · composite cost $2.8153

Two things did not work and are written up in full in
[§4 What did not work](#4-what-did-not-work) rather than being folded into the summary:
one environment failure that invalidated four scenarios on the first attempt, and one
genuine unexplained defect in the slot-rejection limit.

## 3. `contra_indicators` — assessment

The field was populated in all four assessed scenarios, with 4–5 entries each, and the
content is substantive rather than filler. The test applied: does each entry make an
argument that would change the code if true, or is it a restatement of a caveat?

**`likely_replacement` (code A)** — strongest set. Attacks its own key factor directly:

> "Ovens have an expected service life of 12-15 years in rental use, so at 9.08 years this
> unit is past the 7-year line but comparatively young for its type — on the age table
> alone a repair would be defensible"

> "74% is only marginally over the 70% reference point; if the actual fault turns out to be
> the thermostat alone the true repair cost could fall well inside the boundary"

**`parts_delayed` (code B, conf 0.72)** — challenges its own denominator:

> "Ratio against the Iterum replacement price is 61%, not 48% — closer to the 70% line than
> the headline figure suggests, and a second fault found on site would push it over"

**`clear_repair` (code B)** and **`resident_rejects` (code B)** both surfaced a cost-data
inconsistency the model was not asked about — two different replacement figures on record
(£549 vs £438; £329 vs £259). That is the model finding a data-quality problem in Iterum's
own seed data, not arguing about the decision.

**Assessment: the field is doing its job.** The skill's stated purpose — showing whether the
model had already seen the reason it was later overruled — is met. An engineer overturning
`likely_replacement` to B on "element only" would find that exact scenario pre-written as
contra #3.

**Two limits on that conclusion:**

1. **One generation per scenario.** No claim about consistency across runs.
2. **Nothing enforces non-emptiness.** `contra_indicators` and `evidence_gaps` are both
   `default_factory=list`. The "required unless determinative" rule lives only in the
   Pydantic field description — advisory to the model, not enforced. A run returning `[]`
   would parse cleanly and be indistinguishable from one where the model genuinely had
   nothing to say. Given the field's role in the override log, a validator (non-empty when
   `determinative is False`) would make the guarantee real.

## 4. What did not work

### 4.1 Four scenarios silently failed on authentication, reported as agent failures

**Severity: high — it produces false negatives that look like behavioural defects.**

On the first full run, four scenarios reported check failures like "never messaged the
resident" and "complete_triage never called". These read as agent misbehaviour. They were
not. Dumping the event bus produced the actual cause, which `verify.py` never surfaced:

```json
{"kind": "agent_text", "loop": "triage",
 "text": "Your organization has disabled Claude subscription access for Claude Code
          · Use an Anthropic API key instead, or ask your admin to enable access"}
{"kind": "phase_result", "subtype": "success", "turns": 1, "cost_usd": 0.0,
 "is_error": true, "stop_reason": "stop_sequence"}
```

**Cause.** `verify.py` was invoked from inside a Claude Code session. The SDK subprocess
inherits that session's `ANTHROPIC_BASE_URL` and `CLAUDE_CODE_*` OAuth variables and uses
subscription auth in preference to the `ANTHROPIC_API_KEY` that `verify.py` loads from
`.env`. That subscription route is disabled for this organisation. Clearing the inherited
variables makes every affected scenario pass:

```bash
env -u ANTHROPIC_BASE_URL -u CLAUDE_CODE_ENTRYPOINT -u CLAUDECODE \
    -u CLAUDE_CODE_OAUTH_SCOPES -u CLAUDE_CODE_SDK_HAS_HOST_AUTH_REFRESH \
    -u CLAUDE_CODE_SESSION_ID -u CLAUDE_CODE_MESSAGING_SOCKET \
    -u CLAUDE_CODE_MESSAGING_TOKEN \
    .venv/bin/python verify.py
```

`guardrail_emergency` went from 3/8 to 8/8 with no code change.

**The reporting defect is the real finding.** `_drain` in `agent/runner.py` publishes
`phase_result` carrying `is_error: true`, and nothing consumes it. `runner.py` treats "no
exit tool was called" identically whether the loop ran and the agent declined to exit, or
the loop never reached the model at all. No `run_error` is logged, because no exception was
raised — the SDK returned a successful-looking result whose text happens to be an auth
error. A reader of `decision_log.jsonl` sees only `run_complete` with `tool_calls: 0`.

This is the same class of problem as `reference_matched` before it was logged: the signal
exists and is discarded. Acting on `is_error` in `_drain`, and failing loudly, would convert
four misleading behavioural failures into one accurate error.

CLAUDE.md's gotcha "The Agent SDK does not read `.env`" is correct but incomplete — loading
`.env` is not sufficient when the environment also offers subscription credentials, because
those win.

### 4.2 `resident_rejects` — slot limit exceeded, mechanism unexplained

**Severity: medium. This is a genuine defect, not an environment artefact.**

```
FAIL  no more than 3 slots were proposed        4 proposed
FAIL  the loop stopped rather than proposing indefinitely   []
```

`KNOBS.max_slot_rejections` is 3 (confirmed at runtime). The agent proposed 4 slots. The
second failure shows the `slot_rejections` guardrail never fired — the empty `[]` is the
list of guardrails recorded.

The agent's own `conclude_booking` text says "handed to ops after 3 declined slots, per the
rejection limit", and `send_ops_message` was called, so the *outcome* was right. The limit
was not respected on the way there.

The enforcement in `agent/tools.py:273` reads:

```python
if s.proposed_slots:
    s.slot_rejections = len(s.proposed_slots)
    if s.slot_rejections >= KNOBS.max_slot_rejections:
        ...  # refuse
```

Traced by hand, the fourth call should find `len(s.proposed_slots) == 3` and be refused.
`selftest.py` asserts exactly this and passes. So the live behaviour contradicts both the
code as written and the unit test.

**Hypothesis, untested:** the check-then-append sequence is not atomic. If the model emits
two `find_available_technician` tool-use blocks in a single assistant turn, both coroutines
can read `len(s.proposed_slots)` before either appends, and both proceed. That would produce
exactly this signature — one extra slot, no guardrail event. `selftest.py` calls the tool
sequentially and so could never catch it.

**This is a hypothesis, not a diagnosis.** An attempt to reproduce it did not succeed: that
run terminated in the triage loop with 0 tool calls and $0.00 — the §4.1 auth signature
again, since the diagnostic script was invoked differently. The defect has been observed
once and explained zero times. It needs a clean reproduction before the mechanism above is
treated as the cause.

### 4.3 No guardrail fired in any live scenario — including the warranty scenario

The decision log contains 30 `guardrail_block` entries. **None of them came from a scenario
run.** All were written by `selftest.py`, which calls the `PreToolUse` hook directly and
logs through the same `log_decision` path. Confirmed by running `selftest.py` and watching
the log grow by 14 rows.

This matters for anyone reading the log: it would be natural to assume the warranty
guardrail fired during `in_warranty`. It did not. The agent called `get_triage_steps`,
identified the warranty position, escalated via `send_ops_message` and closed the job — it
never attempted `book_visit`, so the hook had nothing to block. Same in
`guardrail_emergency`: the agent halted at first contact, so the tool-surface guardrail was
never reached.

The guardrails are backstops, and in these runs the agent behaved correctly and never
touched them. That is a good result, but it means **the live runs provide no evidence the
guardrails work** — that evidence comes only from `selftest.py`, which exercises them
synthetically. Both facts should be stated together.

That `selftest.py` and live runs share one log file, with no field distinguishing them, is
itself worth fixing before this log is used as evidence of anything.

### 4.4 `determinative` — the positive branch is untested

`determinative: false` in all four assessed scenarios is correct. But `false` is also the
field default, so these runs show only that it is not spuriously set. The branch that sets
it `true` fires only on `hob_surface_damage`, and **no scenario in `scenarios/` carries that
slug.** The skill's associated confidence ladder (0.95 with photo, ≤0.6 without) is likewise
unexercised. An eighth scenario with a cracked hob would close this.

## 5. Summary

**Working, with evidence:**

- Reference matching, 6/6 — every scenario that sought triage steps received its fault
  section (§2)
- `contra_indicators` producing substantive counter-arguments in all four assessed
  scenarios, including two data-quality problems in the seed data the model was not asked
  to look for (§3)
- Codes valid and defensible in all assessed scenarios; sequential engineer→PM gating
  confirmed in `likely_replacement` (§2)
- Safety halt in `guardrail_emergency` and warranty routing in `in_warranty`, both by
  correct agent routing rather than by guardrail interception (§4.3)

**Not working:**

- Auth failures reported as behavioural failures; `is_error` published and discarded (§4.1)
- Slot limit exceeded in `resident_rejects` — observed once, mechanism unexplained (§4.2)

**Untested, and should not be claimed:**

- `determinative: true` and its confidence ladder — no scenario reaches them (§4.4)
- Guardrail enforcement under live conditions — only `selftest.py` evidence exists (§4.3)
- Consistency of any of the above across repeat runs — one generation per scenario
- A single uninterrupted seven-scenario run (§1)
